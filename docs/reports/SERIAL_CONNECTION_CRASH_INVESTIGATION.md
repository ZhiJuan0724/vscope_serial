# 串口连接闪退排查报告

## 问题概述

部分从 `1.0.6-beta5` 及更早版本升级的用户，在连接 CP210x 串口时遇到应用进程直接退出。相同的 beta.4 发布包和同类 CP210x 设备在开发机上可以正常连接。

故障电脑上的主要表现：

- beta.4 完整包连接时闪退；
- 将完整包放到新目录仍然闪退，排除旧目录配置和升级残留；
- 单独替换不同版本的 `native_serial_reader.dll` 仍然闪退；
- 当前工作区构建的 beta.5 完整包可以正常连接。

## 排查结论

本次问题不是 CP210x 型号、串口参数、驱动缓冲区大小或单个 DLL 版本导致的普通连接失败。现有证据指向特定电脑上的 FFI/原生全局状态初始化顺序与串口打开 isolate 之间存在时序竞态，但在取得崩溃转储前，这仍是强工作假设而不是已经完成底层归因的最终结论。

如果连接前先同步输出 TRACE 或 DEBUG 日志，再进入关键 FFI 调用，部分电脑会在 Dart 与原生 DLL 的边界发生无法被 Dart `try/catch` 捕获的原生异常，导致整个应用进程退出。

beta.5 开发代码在连接前增加了 `configureDiagnosticLogging()` 原生调用，该调用改变了进入关键连接流程前的原生调用顺序，因此闪退消失。真正起作用的不是诊断日志内容。

目前能够确认“启动最早阶段显式调用 `_nsrIsOpen()`”可以稳定解决问题。需要注意，`v1.0.7-beta.4` 已经会在启动的端口监听初始化中调用 `_nsrInitDartApi` 和 `_nsrStartPortMonitor`，因此不能把试验结果泛化成“任意 FFI 调用都能预热成功”。更准确的解释是：`_nsrIsOpen()` 的调用时机、具体入口或它对原生全局状态的读取消除了后续竞态；更底层机制仍需崩溃转储或在故障电脑上逐提交二分才能确认。

## 历史版本边界

- 原生串口 FFI 由提交 `9ddd6d9` 引入，位于 `v1.0.0` 之前；之后的正式版本都使用了该原生链路。
- 同一故障电脑已确认 `v1.0.6-beta.5` 可以正常连接，而 `v1.0.7-beta.4` 可以复现闪退。因此不能用“是否调用过 FFI”直接判定某个历史版本是否受影响。
- 两个版本之间先后引入了原生端口监听、连接协调器、`SerialTransport` 抽象、后台关闭与写入 isolate，以及日志和全局异常链调整。这些改动会改变首次 FFI 调用附近的 AOT 布局与调度时序，但现有对照试验不足以把根因归入其中某一个提交。
- `v1.0.7-beta.4` 的启动端口监听本身已经调用原生 FFI；这排除了“该版本直到点击连接才发生进程内第一次 FFI 调用”这一过度简化的解释。
- 当前可作出的版本判断是：`v1.0.7-beta.4` 属于已确认复现版本；`v1.0.6-beta.5` 属于该电脑上的已确认正常版本；其它从 `v1.0.0` 到 `v1.0.7-beta.3` 的版本只有潜在风险，尚未逐版完成同机验证。
- `0133341` 之后的开发代码在连接阶段先调用 `configureDiagnosticLogging()`，可偶然提前初始化 FFI，但这只是被动规避；只有独立的启动预热才能作为后续正式版本的修复边界。

## 对照测试

| 测试项 | 结果 | 结论 |
| --- | --- | --- |
| 将 `SetupComm` 缓冲区恢复为旧版 `1/1` | 闪退 | 排除 64 KiB 缓冲区 |
| 单独替换多个版本的原生 DLL | 闪退 | 排除单纯 DLL 版本问题 |
| beta.4 源码使用当前工具链全新构建 | 闪退 | 排除旧构建工具链 |
| A：恢复 beta.4 的 isolate 单 `bool` 返回 | 成功 | 排除 isolate 返回结构 |
| B：删除连接前的原生诊断配置调用 | 闪退 | 连接前原生预调用是稳定条件 |
| C：TRACE 和 DEBUG 同时常开 | 闪退 | 同步日志会改变并触发竞态时序 |
| E：使用无副作用 `_nsrIsOpen()` 代替诊断配置进行预热 | 成功 | `_nsrIsOpen()` 可作为稳定规避，不能据此推广到任意 FFI |
| F：仅 TRACE 常开 | 闪退 | TRACE 本身即可触发竞态 |
| G：仅 DEBUG 常开 | 闪退 | DEBUG 本身即可触发竞态 |
| H：应用启动时预热，同时 TRACE/DEBUG 全开 | 成功 | 启动预热是稳定且与日志开关无关的修复 |

## 闪退时机说明

部分测试中，连接窗口尚未在画面上消失应用就已经退出；另一些测试中，连接窗口先关闭，左下角显示“连接中”后才退出。

连接按钮会先调用 `service.connect()`，随后执行 `Navigator.pop()`。如果异常发生在事件循环进入下一帧之前，窗口虽然已经执行关闭逻辑，但画面还未来得及刷新，因此看起来像是“窗口尚未关闭就闪退”。如果异常发生在后台串口打开阶段，界面则有机会先显示“连接中”。

两种视觉表现对应不同的触发时机，不代表存在两个独立根因。

## 正式修复建议

1. 在应用启动最早阶段执行一次已经由故障电脑验证有效、无副作用的 `_nsrIsOpen()` 调用。
2. 预热应位于 `WidgetsFlutterBinding.ensureInitialized()` 之后、日志系统初始化和串口发现启动之前。
3. 预热接口不得打开串口、枚举设备、修改串口状态或启动线程，建议只调用只读的原生状态查询。
4. 预热失败时应记录可诊断信息，但不能导致应用启动失败。
5. 串口连接流程不应继续依赖 `configureDiagnosticLogging()` 的偶然预热副作用。
6. TRACE/DEBUG 调试模式应保持可用；启动预热完成后，开启调试日志不应影响串口连接稳定性。

## 不需要实施的改动

- 不需要将 `SetupComm` 永久恢复为 `1/1`；
- 不需要增加驱动缓冲区兼容设置；
- 不需要针对 CP210x 单独建立连接分支；
- 不应继续通过单独替换 DLL 的方式处理该问题，发布包中的 exe、`app.so` 和 DLL 应来自同一次干净构建。
